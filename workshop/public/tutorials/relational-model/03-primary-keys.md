## Objetivo del paso

Si dos clientes se llaman Ana García, ¿cómo sabe la aplicación de cuál hablas? Necesita un dato que identifique a cada fila **sin ambigüedad**. En este paso aprendes:

1. Qué es una **clave primaria** y qué garantiza.
2. Por qué casi siempre se usa un `id` generado en lugar de un dato "natural" como el email.
3. Qué es una clave primaria **compuesta**.

## La clave primaria

:::concept Clave primaria (primary key)
La **clave primaria** es la columna (o combinación de columnas) que identifica a cada fila de una tabla. La base de datos garantiza dos cosas:

- **Es única**: no puede haber dos filas con el mismo valor.
- **Nunca es `NULL`**: toda fila tiene que tenerla.

En el panel **Datos**, las columnas de clave primaria llevan el icono de una **llave**.
:::

Todas las tablas de la tienda tienen una. Para buscar una fila concreta, se usa su clave primaria:

```sql run title="El cliente con id 7"
SELECT id, first_name, last_name, email
FROM customers
WHERE id = 7;
```

`WHERE id = 7` significa "solo la fila cuyo `id` es 7". Como `id` es la clave primaria, sabes que la respuesta es **una fila o ninguna**, nunca dos.

## La base de datos hace cumplir la clave

Intenta crear una categoría con un `id` que ya existe (la 1 es Electrónica):

```sql run error title="Un id repetido"
INSERT INTO categories (id, name)
VALUES (1, 'Mascotas');
```

`duplicate key value violates unique constraint "categories_pkey"`: la base de datos rechaza la fila. Tampoco acepta una fila sin clave:

```sql run error title="Un id vacío"
INSERT INTO categories (id, name)
VALUES (NULL, 'Mascotas');
```

## ¿De dónde salen los `id`?

Si la aplicación tuviera que inventar un número libre para cada cliente nuevo, dos altas simultáneas podrían elegir el mismo. Por eso se deja que **la base de datos los genere**. En la tienda, las columnas `id` están definidas así:

```sql
id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

`GENERATED ... AS IDENTITY` hace que PostgreSQL asigne el siguiente número disponible cuando no indicas uno:

```sql run title="Una categoría con id automático"
INSERT INTO categories (name)
VALUES ('Mascotas')
RETURNING id, name;
```

`RETURNING` devuelve la fila recién creada, con el `id` que se le asignó. Ejecútalo dos veces: la segunda fallará, pero no por el `id`, sino porque el **nombre** de la categoría también debe ser único (lo verás en el paso de restricciones). Si quieres volver al estado inicial, usa **Restablecer** en el panel **Datos**.

:::why ¿Por qué no usar el email como clave primaria?
El email es único, así que parece una buena clave "natural". Pero:

- **Cambia.** Si Ana cambia de email, habría que actualizar la clave en `customers` **y en todas las tablas que la usan** (sus pedidos).
- **Es largo.** Las claves se copian en las tablas relacionadas y en los índices: un número ocupa menos y se compara más rápido que un texto.
- **Es un dato personal.** Usarlo como identificador lo esparce por URLs, logs y tablas.

La práctica habitual es una clave **sustituta** (*surrogate*): un `id` sin significado de negocio, que nunca cambia. Que el email no se repita se garantiza aparte, con una restricción `UNIQUE`.
:::

## Claves primarias compuestas

Mira la tabla `order_items` en el panel: tiene **dos** llaves, `order_id` y `product_id`. Su clave primaria es la **combinación** de ambas:

```sql
PRIMARY KEY (order_id, product_id)
```

Eso significa que un mismo producto puede aparecer en muchos pedidos, y un pedido puede tener muchos productos, pero **un producto solo puede aparecer una vez en cada pedido** (si compras tres unidades, es una sola línea con `quantity = 3`).

```sql run title="Las líneas del pedido 14"
SELECT order_id, product_id, quantity, unit_price
FROM order_items
WHERE order_id = 14;
```

Intenta añadir otra vez a ese pedido un producto que ya tiene:

```sql run error title="El mismo producto dos veces en un pedido"
INSERT INTO order_items (order_id, product_id, quantity, unit_price)
SELECT order_id, product_id, 1, unit_price
FROM order_items
WHERE order_id = 14
LIMIT 1;
```

## Retos

::::challenge Buscar un producto por su clave
Muestra el **id**, el **nombre** y el **precio** del producto cuyo `id` es **20**.

:::hint
Igual que la consulta del cliente con id 7, pero sobre `products` y con las columnas `id`, `name` y `price`.
:::

:::solution
```sql
SELECT id, name, price
FROM products
WHERE id = 20;
```
Es la *Bicicleta estática*. Buscar por clave primaria es la consulta más rápida que existe: PostgreSQL usa el índice que crea automáticamente para cada clave primaria.
:::
::::

::::challenge ¿Qué clave elegirías?
Una aplicación de recursos humanos guarda empleados con: DNI, nombre, email corporativo y fecha de contratación. ¿Qué usarías como clave primaria y por qué? ¿Qué harías con el DNI?

:::hint
Piensa en qué datos pueden cambiar, cuáles son personales y cuáles se van a copiar en otras tablas (nóminas, vacaciones…).
:::

:::solution
Un `id` generado por la base de datos (`GENERATED ... AS IDENTITY`). El DNI es único, pero es un **dato personal sensible** que acabaría copiado en nóminas, vacaciones y logs, y puede haberse cargado con un error que luego hay que corregir. El email corporativo cambia si la persona cambia de nombre o de dominio.

El DNI se guarda como una columna normal con una restricción `UNIQUE`: la base de datos sigue garantizando que no se repita, sin convertirlo en el identificador de todo el sistema.
:::
::::

:::recap
- La **clave primaria** identifica cada fila: es **única** y **nunca `NULL`**, y la base de datos lo garantiza.
- Lo habitual es un `id` sin significado (**clave sustituta**), generado con `GENERATED ... AS IDENTITY`.
- Los datos únicos del negocio (email, DNI) se protegen con `UNIQUE`, no se usan como clave.
- Una clave **compuesta** combina varias columnas, como `(order_id, product_id)` en las líneas de pedido.

:::
